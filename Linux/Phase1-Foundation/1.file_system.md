# Linux File System

Everything — every file, every directory, every device, every partition, even hardware — lives under a single root directory called `/` (pronounced "_slash_" or "**root**"). There is exactly one top of the tree, and everything branches off from it.

This structure isn't arbitrary — it's governed by a written specification called the **Filesystem Hierarchy Standard (FHS)**, maintained by the Linux Foundation. It's why a /etc directory means roughly the same thing on _Ubuntu, Fedora, Debian, and Arch_.

## In-depth Analysis

![file](../../resources/assets/filesystem.png)

#### 1. Essential Binaries

/bin holds the essential command binaries — the programs every user needs and that must be available even when the system is in a minimal state. Think ls, cp, mv, cat, bash. /sbin is the same idea but for system binaries: administrative tools meant primarily for the root user, like fsck (filesystem check), reboot, ip, and mount. The "s" stands for "system," not "secure," which is a common misconception. /lib contains the shared libraries those binaries depend on — the Linux equivalent of Windows DLLs — along with kernel modules in /lib/modules.
The reason these three sit directly under root, rather than under /usr, is historical and important: the system must be able to boot and reach a basic repair state using only the root filesystem, before anything else is mounted. If /usr lived on a separate disk that failed to mount, you'd still need ls and fsck to fix things. So the "essential for boot and recovery" tools were kept on the root partition.

The great duplication: /usr and the usr-merge
Here's the part that confuses almost everyone. There is also a /usr/bin, /usr/sbin, and /usr/lib. So why two of each?
The answer is a famous accident of history. In the 1970s, the Unix developers ran out of disk space on their primary drive and simply mounted a second disk at /usr to hold the overflow of user programs. The split between /bin and /usr/bin was never a deliberate design — it was a storage hack that calcified into a standard. The intended distinction became: /bin and /sbin hold what's needed to boot and repair; /usr holds the bulk of the system's programs and data that aren't critical to early boot.
/usr (which stands for "Unix System Resources" in the modern reading, though it originally meant "user") is itself a large hierarchy that mirrors root: /usr/bin, /usr/lib, /usr/local (for software you compile or install manually, kept separate from the distribution's package manager so updates don't clobber it), /usr/share (architecture-independent data like documentation, icons, and man pages), and /usr/include (C header files for development).
Modern distributions have largely abandoned the old split through what's called the usr-merge: /bin is now just a symbolic link pointing to /usr/bin, /sbin points to /usr/sbin, and so on. Everything physically lives under /usr, and the root-level directories are kept only for compatibility. This happened because modern boot systems (the initramfs) already mount /usr before it's needed, making the original separation pointless. So on a current Ubuntu or Fedora system, /bin and /usr/bin are literally the same directory.

Configuration: /etc
/etc is where all system-wide configuration lives, and it follows one ironclad rule: it contains only static configuration files, never binaries. Pronounced "et-see" or "etcetera," this is the directory you'll edit most as an administrator. It holds things like /etc/passwd (user accounts), /etc/fstab (which filesystems to mount at boot), /etc/hostname, network configuration, and the config files for nearly every installed service. The key conceptual property: /etc is host-specific — it describes the configuration of this one machine and is not meant to be shared with other machines.

Variable data: /var, /tmp, /srv
This group is defined by one shared property: the data here changes during normal operation. This contrasts sharply with /usr, which is meant to stay static (read-only, even) once installed.
/var ("variable") holds data that grows and changes: system logs in /var/log, the print and mail queues in /var/spool, package manager caches in /var/cache, databases, and website files for some server setups in /var/www. When a disk fills up unexpectedly, /var/log is usually the first place to look.
/tmp is for temporary files that programs create during execution. The crucial thing to know is that /tmp is typically wiped on reboot (and on many modern systems it's a RAM-backed filesystem that never touches disk), so never store anything there you want to keep. There's also /var/tmp for temporary files that should survive a reboot.
/srv ("service") holds data served by the system to the outside world — for example, the files served by a web or FTP server. It's somewhat underused; many setups put web content in /var/www instead, but /srv is the FHS-blessed location.

The virtual filesystems: /proc, /sys, /dev, /run
This group is conceptually the most interesting because these directories don't exist on disk at all. They are virtual filesystems that the kernel generates in memory and presents as files. They embody the deepest Unix philosophy — "everything is a file" — by exposing the running system's internal state as readable, sometimes writable, files.
/proc ("process") is a window into the running kernel and every running process. Each process gets a numbered directory (/proc/1234/) containing its status, memory maps, and open file descriptors. Files like /proc/cpuinfo and /proc/meminfo describe your hardware. You can cat /proc/cpuinfo right now to see your CPU details — that file occupies zero bytes on disk; the kernel produces its contents on the fly each time you read it.
/sys ("sysfs") is a newer, more structured cousin of /proc, exposing information about devices, drivers, and kernel subsystems. It's where you'd adjust things like screen brightness or read battery status by writing to files.
/dev ("devices") contains device files — special files that represent hardware and pseudo-devices. /dev/sda is your first disk, /dev/null is the famous "bit bucket" that discards anything written to it, /dev/zero produces endless zero bytes, and /dev/random produces random data. Reading from and writing to these files is how programs talk to hardware.
/run holds runtime data about the system since the last boot — process IDs of running services, sockets, and lock files. Like /tmp, it's memory-backed and cleared on every boot. It exists to give early-boot processes a place to write state before the disk-based filesystems are even available.

User space and add-ons: /home, /root, /opt
/home is where regular users' personal directories live — /home/alice, /home/bob — each containing that user's documents, downloads, and per-user configuration (the hidden "dotfiles" like .bashrc). This is the equivalent of C:\Users on Windows.
/root (note: distinct from /, the root directory) is the home directory for the root/administrator user specifically. It's deliberately not placed under /home because /home is sometimes on a separate partition that might not be mounted during recovery, and the administrator needs a usable home directory even then.
/opt ("optional") is for self-contained third-party software packages that don't follow the standard distribution layout — often large commercial applications that prefer to keep everything (binaries, libraries, config) bundled in one place like /opt/google/chrome.

Boot and mounting: /boot, /mnt, /media
/boot contains everything needed to start the system before the main filesystem is up: the Linux kernel image itself (vmlinuz), the initial RAM disk (initramfs), and the bootloader configuration (GRUB). This is frequently on its own small partition.
/mnt is a conventional, generic mount point — historically where an administrator would temporarily mount a filesystem by hand. /media, by contrast, is where the system automatically mounts removable media like USB sticks and DVDs when you plug them in, typically creating a subdirectory named after the device or its label.

The two axes that tie it all together
If you want to truly internalize the FHS rather than memorize it, the standard organizes everything along two conceptual axes, and almost every directory's placement follows from where it falls on these:
The first axis is static versus variable. Static data doesn't change without administrator action — binaries in /usr, config in /etc. Variable data changes during operation — logs in /var, temp files in /tmp. This separation lets you mount /usr as read-only for security and stability while keeping the writable parts elsewhere.
The second axis is shareable versus unshareable. Shareable data could be served over a network to multiple machines — /usr and /opt can be shared from one server to many clients. Unshareable data is specific to one host — /etc (this machine's config) and /boot (this machine's kernel) make no sense to share.
Once you see a directory through these two lenses, its location stops feeling arbitrary. /var/log is variable and unshareable. /usr/share is static and shareable. The whole hierarchy snaps into a logical grid.
A good next step, if you want to make this concrete, is to open a terminal and explore. Run ls -l / to see the top level (watch for the symlinks from the usr-merge), then cat /proc/cpuinfo and cat /proc/meminfo to feel the virtual filesystem in action, and man hier to read your system's own manual page describing this exact hierarchy.
